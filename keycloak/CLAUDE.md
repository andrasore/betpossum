# CLAUDE.md — Identity (Keycloak)

`/keycloak` builds the Keycloak image and ships the realm definitions imported
at container start. Keycloak owns **all** authentication.

## Files

- `Dockerfile` — two-stage build off `quay.io/keycloak/keycloak:26.0`;
  `kc.sh build` with `KC_DB=postgres`, then `start --optimized --import-realm`.
- `realm.template.json` — **the** `betting` realm. One file for every
  environment, with three placeholders: `__PUBLIC_ORIGIN__`,
  `__CORE_CLIENT_SECRET__`, `__SSL_REQUIRED__`.
- `render-realm.sh` — the container entrypoint in **all** stacks. Substitutes
  the three placeholders from `PUBLIC_ORIGIN` / `KEYCLOAK_ADMIN_CLIENT_SECRET` /
  `SSL_REQUIRED`, writes the result to `/opt/keycloak/data/import/realm.json`,
  then execs `kc.sh`. It fails loudly if a placeholder is left unsubstituted.
- `healthcheck.sh` — container healthcheck used by the Coolify stack; fetches
  the realm's OIDC discovery document over bash `/dev/tcp`.

Per-environment values are set in the compose files, and are the **only**
difference between environments:

| | `PUBLIC_ORIGIN` | `SSL_REQUIRED` | `KEYCLOAK_ADMIN_CLIENT_SECRET` |
|---|---|---|---|
| dev | `http://localhost:8080` | `none` | `betting-core-secret` |
| e2e | `http://localhost:18080` | `none` | `betting-core-secret` |
| prod | `https://<domain>` | `external` | generated by Coolify |

## Realm shape

- Realm `betting`, two roles: `admin` (gates admin pages/endpoints) and `user`
  (default for everyone).
- Two clients:
  - `betting-frontend` — **public**, PKCE; used by the SPA.
  - `betting-core` — **confidential**, service account; Core uses it to call the
    admin API for user email/name lookups.
- Keycloak runs against its **own `keycloak` database** (own role/credentials)
  on the shared Postgres instance, separate from the app's `betting` database.
  Infra's `postgres/init.sh` provisions it.

## Conventions

- **Realm config is import-only.** Edit the `realm*.json` files and let
  `--import-realm` apply them on boot; don't hand-tweak through the admin UI and
  expect it to persist — changes there are lost on the next clean boot.
- **`--import-realm` only imports a realm that does not already exist.** Once the
  `betting` realm is persisted in the `keycloak` database (now a database on the
  shared `postgres` container, no longer a dedicated volume), edits to
  `realm.json` (a new `loginTheme`, client, role, mapper…) are **silently
  ignored** on a plain `docker compose up -d keycloak`. To pick up dev realm
  changes, drop and recreate just the `keycloak` database, then re-import — this
  leaves the app's `betting` data intact (a full `down -v` would wipe both):
  ```bash
  docker compose stop keycloak
  docker compose exec -T postgres psql -U betting -c 'DROP DATABASE keycloak;'
  docker compose exec -T postgres psql -U betting \
    -c 'CREATE DATABASE keycloak OWNER keycloak;'
  docker compose up -d keycloak
  ```
  The e2e stack is unaffected — its global-setup uses fresh volumes each run, so
  every e2e run re-renders and re-imports the realm clean.
- **There is one realm file.** Add roles, clients or mappers to
  `realm.template.json` and every environment gets them. This replaced three
  near-identical files that had to be kept in step by hand — and had already
  drifted in whitespace and escaping. If you need a new per-environment value,
  add a placeholder and wire it through `render-realm.sh`; don't fork the file.
- **The production client secret is never committed.** Dev and e2e pass the
  literal `betting-core-secret`; production passes Coolify's generated
  `SERVICE_PASSWORD_CORECLIENT`. Keycloak's own `${VAR}` substitution for import
  files is documented but has never worked (keycloak/keycloak#20199), which is
  why the render step exists at all.
- Services verify JWTs against this realm's JWKS (RS256) and check
  `realm_access.roles`. Keycloak is fronted by nginx under the `/kc` path
  prefix (`KC_HTTP_RELATIVE_PATH=/kc`) so the browser stays single-origin;
  services reach it backchannel via `KEYCLOAK_INTERNAL_URL`
  (`http://keycloak:8080/kc`). The browser-facing issuer is
  `http://localhost:8080/kc/realms/betting` (dev), and
  `${PUBLIC_ORIGIN}/kc/realms/betting` in production.
- **`KC_HOSTNAME` is what determines the advertised scheme**, not the proxy
  headers. With `KC_HOSTNAME` set to an absolute `https://…` URL, the issuer and
  every endpoint in the discovery document are `https://` regardless of what
  `X-Forwarded-Proto` says — verified directly. So if the issuer comes back
  `http://` in production, the bug is `PUBLIC_ORIGIN`, not nginx.
